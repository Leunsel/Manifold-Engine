## Step 5: live checks

**A 32-bit game, 2026-11-25, read-only probe with `--dry-run` (no writes, no agent):**
- Native RTTI x86 works live: 6 classes of the game's engine, 38 objects in 0.24 s.
- Signature Maker (code only, module): 18 of 18 functions get a verified signature.
- **L1 (new):** `getUniqueAOB` returns `nil` for 10 of 18 virtual functions, while the Signature Maker finds a unique pattern of 11 to 99 bytes for 19 of 20 of them. Mostly functions with an SEH prologue (`55 8B EC 6A FF 68 ?? ?? ?? ?? 64 A1 00 00 00 00`). Suspected cause: `getUniqueAOB` gives up at 64 or more hits of the seed and masks differently. No wrong result, but none at all. Proposal: base `getUniqueAOB` on the measurement of `MakeSignature` (`Source/Disasm/UniqueAob.cpp`).

**The same game, Code Filter live (85b9a50):** Collect found 21,210 functions (no unwind data on x86, so exports and function pointers; call targets off in the ini). In the Filter Out round the game stopped responding: 176 functions ran in about 80 s, then the round was stopped.
- Read from outside (reading only): the agent is clean. `active 0`, 230 hits, 20,980 released, no entries being reset. All 21,210 bytes are back to the original, no int3 is left. Neither the Windows debugger nor a break.
- 43 threads are suspended at the same place in ntdll without game frames (probably idle pool threads). The main thread sleeps in a loop in the game's module.
- **L2 (open, cause unclear):** suspect 1 is the candidates from "Function Pointers" (relocations), which had never been armed in this game: an int3 in the middle of an instruction changes it silently. Suspect 2 is the agent changes of step 4. Next step: an A/B test with and without "Function Pointers".
- **L2, cause (A/B test):** without "Function Pointers" the filter ran down to 17 functions without a freeze. The cause is jump and index tables that 32-bit MSVC puts into `.text`. Their addresses are relocated immediates (`jmp [eax*4+table]`). They were taken for function starts, and an int3 inside one silently changes a jump target.
- **L2, fix (`e12b300`):** without known function bounds, a pointer target is only armed when a data section names it (a vtable, a function table). Targets that only an instruction names are never armed, whatever the settings. A table check comes on top: a target that is itself a slot, holds a code pointer or holds index bytes counts as data. The tests in TestTarget (naked functions as tables in `.text`) fail three times without the rules and are green with them.
- **L2, check live (installed `e12b300`):** the Code Filter runs cleanly in the game with "Function Pointers", without a freeze. **L2 done.**
- **Backups, folder name:** the session made a backup in a folder named after the table plus a hash, as planned. The old folder without a hash is still there. Checked from outside only.
- **The agent unloads itself:** after the program closed, `ManifoldAgent32.dll` is no longer in the game. The Code Filter had loaded it before. Checked read-only with `EnumProcessModulesEx(LIST_MODULES_32BIT)`, 123 modules; as a cross-check the game's own modules are in the list. The game keeps running. `tasklist /M` only sees the 64-bit modules under WOW64, so it is no proof.
- **Exit code 0xCFFFFFFF** (Windows ends a program that stopped responding) and 0xC000013A (Ctrl+C) no longer count as a crash. The crash report names them.
- **Three crashes of the game at one address:** they came from a separate experiment with a manual mapper (according to the maintainer) and do not belong to this list.

**A 64-bit Unreal Engine game, 2026-11-25, read-only:**
- `--unreal-check`: 49,587 objects, 5,716 types in 0.5 s. Engine, world, controller and pawn found; the pawn dissected into 627 fields in 1 ms. Works as on 2026-11-19.
- Pointer Scanner on the pawn, 5 levels: 2.3 GB read, 5.0 million pointers, map 0.22 s (10.6 GB/s), search 0.09 s, 0.6 to 1.1 million paths. On an immediate rescan 50 to 90 % still lead to the pawn. Paths of 2 levels all stay; the rest go through memory that changes all the time in a running game.
- **L3 (fixed, `2a650ec`):** the Pointer Scanner crashed in about 1 of 6 runs with 0xC0000005, without output and without a dump. The cause was `Process::Read`: with the address in the last page of the address space (a sentinel like `0xFFFF…F0` plus an offset in the rescan), the page end overflowed to 0, and the zero fill wrote up to 4 KB behind an 8-byte buffer on the stack. Fix: a range past the end of the address space is not read, and the page loop computes without overflow. The same arithmetic was in `StructureWindow.cpp` (snapshots in Dissect) and is fixed there too. The test `ReadAtTopOfAddressSpace` (suite structures) crashes without the fix just like the game run and is green with it. Live afterwards 20 of 20 runs clean.
- New tool: `MANIFOLD_TEST_TRACE_FAULTS=1` makes Tests.exe write every fault with its stack (module+offset) unbuffered to stderr. That helps with crashes that get past the crash dump. Resolve with `llvm-symbolizer --obj=Manifold-Engine.Tests.exe --adjust-vma=0` and address 0x140000000 plus the offset.
- **Observation (open):** reading the 2.3 GB raised the game's working set from 626 MB to 2.9 GB (2.5 GB private). Pages the game committed but never used are really put into RAM by the reads. Not a bug in the game, but it changes its memory figures; Cheat Engine does the same. Skipping pages that are not resident (`QueryWorkingSetEx`) would be possible, only as an option, because paged-out pages hold real data.

**A 32-bit .NET Framework game, 2026-11-25, read-only (`--clr-dump`, dry run, in a world):**
- Classes: the main class with 1,044 statics (1,042 with storage) and the player class with 1,137 fields, each under 8 ms. The player's update method is compiled and named back from its code address.
- The own character: `player[0]` with health, mana, name and position. Read directly and through paths (`manifold.dotnet.value`), both give the same.
- Heap walk on the real game heap (the first time in a world): 4,887,741 objects, 392.7 MB, 17 segments, 0.10 s. Three walks in a row give the same numbers.
- Cross-check: 270 of 270 player, 2,607 of 2,607 NPC and 20,000 of 20,000 item instances are really objects of exactly that class according to `object()`. 17 active NPCs in the main NPC array.
- No fault with `MANIFOLD_TEST_TRACE_FAULTS=1`, exit 0, the game keeps running.
- Observation: the walk skips 73,888 words (about 290 KB, 0.07 % of the heap) on which no valid object starts. Probably the unused ends of the threads' allocation contexts. The cross-check is clean anyway, so nothing to do.

**L1, fix (`e374822` + `771a949`):** `getUniqueAOB` now uses the Signature Maker's measurement with its default masks.
- No limit of 64 hits any more.
- The pattern may also start after the address; the offset is then negative.
- Minimum length 8 bytes.
- "Unique" now means in all memory, like `AOBScan` without flags. Before, only executable memory counted, and a copy in data could be found first.
- Test `SharedPrologue`: 70 functions share their first 120 bytes. The old search fails 3 checks, the new one is green.
- Check live in the 32-bit game (freshly started, 15 functions from vtables, dry run): 15 of 15 get a pattern that `AOBScan` finds exactly once at the right place. 0.13 to 0.50 s per call, 4.3 s for all. Earlier that day 10 of 18 functions got nil.
- Note: as with the Signature Maker, some patterns run over the `ret` and the int3 padding into the next function. That is unique, but more fragile across updates. An option would be `StopAtFunctionEnd`; it is not switched on, so as not to change behaviour the maintainer chose for the Signature Maker.

**Later, Dissect in the .NET game (reported by the maintainer, `948d7bc` + `ada1519`):**
- **L4:** in the Structure Dissect of a 32-bit .NET game, pointers showed 8 bytes, so two neighbouring references as one value (`P->477347F04775E2D4`). `ManagedFieldType` gave references and `IntPtr` 8 bytes always. Fix: the game's pointer size is a required parameter now. Dissect also reads every pointer field in that width, so structures saved earlier with 8-byte pointers show right as well.
- **L5:** moving a structure or a field into the address list turned an embedded structure (`position`, `velocity` of type `Vector2`) into a single AOB record. Fix: it becomes an address group with `+offset` and one record per field (X, Y), recursively down to Dissect's depth (`Table::AddFieldRecords`).
- Tests: `ManagedPointerWidth` and `EmbeddedToAddressList` in suite structures, the second through a real engine in its own process down to the resolved address of Y. Without the fixes 7 failures, with them green. Suites structures, il2cpp and clr green (642 checks).
- **Pointer size everywhere (the maintainer: applies to Mono, Unreal, .NET and own records):** every place that creates pointer fields was checked.
  - Mono, IL2CPP and .NET go through `ManagedFieldType` (L4).
  - Unreal and RTTI take the pointer size from the runtime.
  - Guessing structures (`GuessFields`) and the type choice in Dissect take the process's.
  - The C/C# and ReClass imports take the process's or the file's.
  - The Lua API was still wrong: `addElement` with `Vartype = vtPointer` set 8 bytes. Now the process's pointer size applies, as in Cheat Engine.
  - Own records of type pointer are always shown by Dissect in the game's width, even when an old structure stored 8 (`FieldWidth`).
- **L6:** the Watch view ("Find Out What Writes") wrote RAX … RIP with 64-bit names for 32-bit games. Fix: `Disasm::RegisterLines` produces EAX … EIP with 8 digits and without R8-R15. The Watch view and the breakpoint window both use it. The disassembler, the stack view and the crash report already named them right.
