# Bug Hunt 2026-11-27

Base: `df02c29`. The hunt covered 12 areas and focused on the 33 commits since the previous hunt (`02fb034..`), which had not been reviewed yet.

Method:
- A suspected bug was treated as a bug only once a test showed it failing on the old code.
- Each fix is the smallest change that makes that test pass, with one commit per bug.
- Every fix was reviewed independently for new bugs in the fix itself. Problems found there were handled the same way.
- What could not be shown with a test is not fixed. It is listed below with a way to show it.
- What needs a design decision is not fixed. It is listed below with the smallest fix and the alternatives.

Evidence:
- **observed**: seen in a test run
- **read**: checked in the code
- **assumed**: neither seen nor checked

## Side findings

- `Docs/LUA-API.md:51/206` still lists `executeCode` without the timeout argument.
- `Docs/MANIFOLD-API.md:232` lists `Name[i]` in `manifold.unreal.walk` for TArray only; since `e63742a` it also works on static arrays.
- The new `executeCode` check without a timeout makes the `integration` and `wow64` suites about 10 s longer each.
- Once, not reproduced: `ManagedDumperTests.cpp:465` (`Classes().size() == 2u` after `--mono-agent=bad-handles`), probably an older flake.
- Explained and fixed: `DebuggerTests.cpp:289` (`windows: the trace did not end, waiting for` the address of `TestTarget.Work`, then 0 steps) failed in about 1 of 5 runs of builds with the activation fixes and in none of 30 without them. A probe at the hang showed the process stopped at `Work`: the tracer read the stop number after setting its breakpoint, so a hit in between looked old and the trace waited for ever. The new layout only made that window more likely to be hit; 40 short traces on `Work` show it in every run.
- Twice in full runs, not in separate runs of the suite: `DebuggerTests.cpp:115` (`in-process: stopped with g_shared = 1442` and `= 1435`, `hits 1`): the 64-bit in-process debugger stopped with the shared counter past the allowed drift of 25. Both times other work used the machine; to show it, run `--filter=inprocess` in a loop under CPU load.
